# OctoAcme Project Management Docs

This directory contains the core project management process documentation used by OctoAcme. Together, these documents define how the team initiates work, plans delivery, tracks execution, manages risks, communicates with stakeholders, releases changes, and reflects on continuous improvement.

## Overview of OctoAcme project management processes

OctoAcme’s project management approach is built around a clear lifecycle: initiation, planning, execution, release, and close/retrospective. The process begins by validating the business need, aligning stakeholders, and defining measurable success criteria through a lightweight Project One-pager and other early planning artifacts. Once the initiative is approved, the team creates a backlog, identifies dependencies, sets acceptance criteria, and defines milestones so work can move forward with clear ownership and accountability.

The delivery model relies on distinct but collaborative roles. Product managers define the outcome and prioritize the work; project managers coordinate plans, schedules, risk management, and stakeholder communication; developers implement and verify features; QA validates acceptance and quality; and stakeholders provide direction, feedback, and approvals. The team’s principles emphasize customer-first decisions, iterative delivery, clear ownership, data-informed decisions, and psychological safety, creating a culture where responsibilities are explicit and continuous learning is supported.

Communication is intentional and consistent. OctoAcme uses daily standups for operational coordination, weekly PM/PdM alignment, regular team status updates, and milestone-based or ad hoc stakeholder communication. Risks and blockers are tracked in a project register, escalated through defined channels, and communicated via a single source of truth so that teams remain synchronized and leadership can act quickly when dependencies or issues arise.

Quality is treated as an ongoing delivery practice rather than a final checkpoint. The team expects small, reviewable pull requests, clear issue links, acceptance criteria, CI checks for tests and linting, security scanning, and quality validation through unit, integration, and end-to-end tests when appropriate. Releases follow structured checklists for staging, smoke testing, deployment, verification, and rollback planning, while retrospectives turn lessons learned into clear action items that improve the process over time.

## How to use these documents

Use the overview and initiation guides when starting a new initiative; move to planning and execution documents once work is approved; and rely on the risk, release, and retrospective guides to manage delivery and improvement over time. These materials are intended to provide a shared operating model that helps teams stay aligned, reduce single points of failure, and increase repeatability across projects.
